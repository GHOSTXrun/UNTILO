OUTCOME-NATIVE COORDINATION

COMPANIES
AS SOFTWARE.

Sarro is a system model for forming temporary, outcome-bound companies. A company receives a measurable result, a fixed treasury, an acceptance policy and an expiry condition. It coordinates agents and human specialists, verifies delivery, settles approved work and dissolves.

The public repository currently contains the Sarro website, wallet/network integration and an interactive product simulation. Production protocol contracts, audits and autonomous settlement are not included in this release. Sections below label design targets separately from implemented code.

02
CONCEPTUAL CORE

SYSTEM MODEL

The primary unit in Sarro is not a permanent organization. It is a bounded execution container created around a single outcome.

COMPANY

= OUTCOME + TREASURY + POLICY + CAPABILITY + EXPIRY

01 / OUTCOME

Specify the result

The request describes what must exist and how acceptance can be measured, rather than prescribing a staffing structure.

02 / BOUNDARY

Cap the exposure

Budget, time window, permissions and review requirements constrain execution before work begins.

03 / PROOF

Verify delivery

Artifacts and evidence are checked against explicit acceptance policy before a contribution becomes eligible for settlement.

04 / EXPIRY

End by default

After settlement, remaining capital returns, temporary permissions expire and the company dissolves while its work record remains.

03
EXECUTION SEMANTICS

LIFECYCLE

01FORM

Parse the requested outcome, acceptance criteria, maximum budget and delivery window.

Draft → Formed
02DECOMPOSE

Convert the outcome into a dependency graph of scoped tasks and required capabilities.

Formed → Planning
03ASSEMBLE

Select agents or human specialists and reserve budget within treasury policy.

Planning → Executing
04VERIFY

Submit artifacts and evaluate them against deterministic or human review gates.

Executing → Review
05SETTLE

Approve eligible contributions, pay accepted work and release unused commitments.

Review → Settled
06DISSOLVE

Return unused funds, revoke temporary permissions and preserve portable proof.

Settled → Closed
DESIGN INVARIANT

No task should be able to spend beyond its allocation, settle without policy approval, or retain company-scoped authority after dissolution.

05
CLIENT INTEGRATION

WALLET CONNECTION

Sarro uses injected EVM providers. It discovers multi-wallet providers through EIP-6963 and retains window.ethereum as a compatibility fallback.

PROVIDER SELECTIONapp.js
function getProvider() {
  const robinhood = announcedProviders.find(item =>
    (item.info.rdns || '').toLowerCase().includes('robinhood')
  );
  return robinhood?.provider
    || announcedProviders[0]?.provider
    || window.ethereum
    || null;
}
eth_accounts

Reads already-authorized accounts during hydration without opening a permission prompt.

eth_requestAccounts

Runs after user interaction and requests access to the selected public address.

eth_chainId

Reads the active chain and drives the wrong-network visual state.

wallet_switchEthereumChain

Requests a switch to Robinhood Chain using hexadecimal chain ID 0x1237.

wallet_addEthereumChain

Offers canonical network parameters when the wallet reports error 4902.

accountsChanged / chainChanged

Keeps header state synchronized without reloading the page.

NO TRANSACTION PATH

The current frontend does not request token approvals, signatures or transactions. Connecting exposes a public address and requests the configured network only.

08
TRUST BOUNDARIES

SECURITY MODEL

IMPLEMENTED

Local key boundary

Private keys remain inside the user's wallet. Sarro never receives, stores or transmits seed phrases or private keys.

IMPLEMENTED

Explicit permissions

Account access and network changes use wallet-native prompts. Rejection returns the interface to a safe disconnected state.

IMPLEMENTED

Read-before-act state

The interface hydrates current accounts and chain state, then subscribes to provider changes.

IMPLEMENTED

Canonical CA

The address is validated as a 20-byte hexadecimal EVM address before copying is enabled.

DESIGN TARGET

Bounded treasury

Production execution should enforce per-company, per-task and total spending limits onchain.

DESIGN TARGET

Audited settlement

Protocol contracts are not production-ready until source, deployment identifiers and independent audit results are public.

USER SAFETY CHECKLIST

  • Confirm the browser address is exactly https://sarro.fun.
  • Read every wallet prompt and reject unexpected approvals, signatures or transactions.
  • Confirm Robinhood Chain and chain ID 4663 before interacting.
  • Verify the complete token contract address, not only the first and last characters.
  • Treat the formation console as a simulation until production contracts are published.

DELIVERY

DEPLOYMENT

Production is served as a static site from the repository's main branch through GitHub Pages with a custom domain and enforced HTTPS.

  1. CHANGE

    Update source files locally. No build step is required for the current release.

  2. VERIFY

    Check JavaScript syntax, responsive layout, internal anchors, external URLs and wallet error paths.

  3. COMMIT

    Commit a focused change to the public repository with a descriptive message.

  4. DEPLOY

    Push main. GitHub Pages publishes the static root and preserves the CNAME mapping.

  5. CONFIRM

    Verify the Pages state is built and request the production URL over HTTPS.
